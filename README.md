# 나만의 프롬프트 관리 프로그램

GitHub 저장소: https://github.com/9um9n99/prompt-manager

파편화된 AI 프롬프트를 체계적으로 관리하기 위한 Python 콘솔 프로그램입니다. 제목, 내용, 카테고리, 즐겨찾기 여부, 조회수를 하나의 프롬프트 데이터로 저장하고, 메뉴 번호를 입력해 추가·조회·검색·즐겨찾기 기능을 사용할 수 있습니다.

## 실행 환경 및 확인 결과

- Python 3.10 이상 권장
- 별도 외부 패키지 설치 없음

## 데이터 구조 설계

프롬프트는 리스트 안에 딕셔너리를 넣는 방식으로 관리합니다.

```python
prompts = [
    {
        "title": "프롬프트 제목",
        "content": "프롬프트 내용",
        "category": "카테고리",
        "favorite": False,
        "view_count": 0
    }
]
```

**리스트와 딕셔너리, 둘 중 하나만으로는 부족한 이유**

- 리스트만 쓴다면: `["제목1", "제목2", ...]`처럼 값만 나열하게 되어, 각 프롬프트의 내용·카테고리·즐겨찾기 여부를 함께 저장할 방법이 없습니다.
- 딕셔너리만 쓴다면: `{"title": "제목1", ...}`처럼 하나의 프롬프트는 잘 표현되지만, 여러 개의 프롬프트를 순서대로 모아 관리할 수 없습니다.

**장단점 비교**

| 구조 | 장점 | 단점 |
|---|---|---|
| 리스트 | 순서가 있어 여러 항목을 추가한 순서대로 관리하기 쉽고, `for` 반복문으로 전체를 순회하기 편함 | 각 항목이 어떤 의미인지 이름만으로는 알 수 없음 (인덱스로만 접근) |
| 딕셔너리 | `title`, `category`처럼 이름(키)으로 값에 접근하므로 각 속성의 의미가 명확함 | 여러 개를 순서대로 모아 관리하는 데는 불편함 |

그래서 여러 개의 프롬프트라는 "전체 묶음"은 리스트로, 프롬프트 하나가 가진 "여러 속성"은 딕셔너리로 표현해 `리스트[인덱스]["키"]` 형태로 접근하는 구조를 사용했습니다.

## 카테고리 설계

카테고리 목록은 `DEFAULT_CATEGORIES`라는 상수에 한 번만 정의하고, `get_all_categories()` 함수가 이 상수와 사용자가 직접 추가한 카테고리를 합쳐서 반환합니다. 이렇게 하면 카테고리를 코드 여러 곳에 중복해서 적지 않아도 되고, 목록을 바꿀 일이 있으면 상수 한 곳만 고치면 됩니다.

- 텍스트 생성
- 이미지 생성
- 영상 생성
- 페르소나
- 자동화
- 기타

프롬프트를 추가할 때는 번호로 선택하거나 `직접 입력`으로 새 카테고리를 만들 수 있고, 새로 만든 카테고리는 이후 카테고리별 조회 목록에도 함께 나타납니다.

## 입력 검증 정책

| 상황 | 처리 방식 |
|---|---|
| 제목, 내용, 검색어, 직접 입력 카테고리가 빈 값 | `get_input()` 함수가 빈 값이 아닐 때까지 반복해서 재입력을 요구함 |
| 이미 등록된 제목과 동일한 제목 입력 | `title_exists()`로 중복을 확인하고, 중복이면 다른 제목을 다시 입력받음 |
| 카테고리 선택 시 숫자가 아닌 값 입력 | "번호를 입력해주세요" 안내 후 다시 입력받음 |
| 카테고리 선택 시 목록에 없는 번호 입력 | "목록에 있는 번호를 입력해주세요" 안내 후 다시 입력받음 |
| 상세 보기·즐겨찾기에서 숫자가 아닌 값 입력 | `.isdigit()`으로 확인 후 "잘못된 번호입니다" 안내하고 함수를 종료함 |
| 상세 보기·즐겨찾기에서 목록 범위를 벗어난 번호 입력 | 인덱스가 `0` 미만이거나 `len(prompts)` 이상이면 안내 후 종료함 |
| 메뉴에서 정의되지 않은 번호나 문자 입력 | else 분기에서 안내 문구 출력 후 메뉴로 돌아감 |

## 함수 역할

| 함수 | 역할 |
|---|---|
| `get_input()` | 빈 값이 들어오지 않도록 반복해서 입력을 받습니다 |
| `title_exists()` | 새 제목이 기존 제목과 중복되는지 확인합니다 |
| `get_all_categories()` | 기본 카테고리와 사용자가 만든 카테고리를 합쳐 반환합니다 |
| `select_category()` | 카테고리 번호 선택과 직접 입력을 처리합니다 |
| `add_prompt()` | 새 프롬프트를 입력받아 리스트에 추가합니다 |
| `show_list()` | 전체 프롬프트 목록을 출력합니다 |
| `show_by_category()` | 선택한 카테고리의 프롬프트만 출력합니다 |
| `search_prompt()` | 제목과 내용에서 검색어를 찾습니다 |
| `show_detail()` | 선택한 프롬프트의 상세 내용을 출력하고 조회수를 증가시킵니다 |
| `toggle_favorite()` | 즐겨찾기 상태를 추가 또는 해제합니다 |
| `show_favorites()` | 즐겨찾기한 프롬프트만 출력합니다 |
| `show_top_viewed()` | 조회수 기준으로 프롬프트를 정렬해 출력합니다 |
| `show_menu()` | 메인 메뉴를 출력합니다 |
| `main()` | 프로그램을 계속 실행하는 전체 반복문을 담당합니다 |

**함수를 이렇게 나눈 이유**: 만약 모든 코드를 `main()` 한 함수에 몰아넣었다면, 예를 들어 "상세 보기" 기능에서 목록을 다시 보여주고 싶을 때 목록 출력 코드를 통째로 복사해야 했을 것입니다. 실제로 `show_detail()`과 `toggle_favorite()`은 `show_list()`를 그대로 호출해서 재사용하고 있습니다. 기능 하나당 함수 하나로 나누면 이렇게 서로 조합해서 쓸 수 있고, 기능 하나를 수정할 때 그 함수만 보면 되므로 유지보수도 쉬워집니다.

## 반복문(while) 설계 의도

프로그램은 `main()` 함수의 `while True` 반복문으로 계속 실행됩니다. `while True`는 조건이 항상 참이므로 무한히 반복되고, 사용자가 `0`을 입력했을 때만 `break`로 이 반복문을 빠져나가 프로그램이 종료됩니다. 이렇게 설계한 이유는 "사용자가 스스로 종료를 선택하기 전까지 계속 메뉴로 돌아온다"는 콘솔 프로그램의 기본 동작을 구현하기 위해서입니다.

같은 방식이 입력 검증에도 쓰였습니다. `get_input()`은 값이 빈 문자열인 동안 반복해서 재입력을 요구하고, `select_category()`는 유효한 번호가 나올 때까지 반복합니다. "조건이 만족될 때까지 계속 물어본다"는 흐름을 표현할 때 `while` 반복문을 사용했습니다.

## 저장 방식과 영속화 설계

현재 버전은 과제 요구사항에 맞춰 데이터를 파일에 저장하지 않습니다. 프로그램 실행 중 추가한 프롬프트와 즐겨찾기 상태는 메모리의 `prompts` 리스트에만 유지되고, 프로그램을 종료하면 초기화됩니다.

나중에 영속화 기능을 추가한다면 **JSON 파일**을 사용하는 방식이 적합합니다. 이유는 현재 데이터가 리스트 안에 딕셔너리를 담은 구조인데, JSON도 배열(`[]`)과 객체(`{}`)로 이루어진 동일한 형태라서 구조를 바꾸지 않고 그대로 저장할 수 있고, 별도 데이터베이스 설치 없이 Python 기본 모듈인 `json`만으로 읽고 쓸 수 있기 때문입니다.

예상 확장 방식:
- 프로그램 시작 시 `prompts.json` 파일이 있으면 읽어서 `prompts`에 불러오기
- 추가/즐겨찾기 변경/조회수 변경이 있을 때마다 JSON 파일에 다시 저장하기
- 파일이 없거나 손상된 경우 기본 프롬프트 3개로 시작하기

## 브랜치 전략

기본 작업 브랜치는 `main`입니다. 과제 요구사항에 따라 "프롬프트 목록" 기능은 `feature/list-view`라는 별도 브랜치를 만들어 그 안에서 작업했습니다.

```bash
git checkout -b feature/list-view
git add main.py
git commit -m "프롬프트 목록 보기 기능(show_list) 구현"
git checkout main
git merge feature/list-view
git push
```

별도 브랜치를 사용한 이유는, 새 기능을 만드는 중간 과정에서 `main` 브랜치는 항상 정상 동작하는 상태로 유지하고 싶었기 때문입니다. 이번 경우 `main`에서 별도 변경이 없었기 때문에 병합은 **Fast-forward** 방식으로 처리되었고, `git log --oneline --graph --all`에서 `HEAD -> main, origin/main, feature/list-view`가 같은 커밋을 함께 가리키는 것으로 확인할 수 있었습니다.

실제 `git log --oneline --graph --all` 출력(일부):

## 병합 충돌 해결 절차

이번 작업에서는 `main`과 `feature/list-view`가 갈라진 지점 이후 `main`에 별도 변경이 없어 실제 충돌은 발생하지 않았습니다. 만약 같은 파일의 같은 줄을 서로 다르게 수정해 충돌이 발생한다면 아래 순서로 해결합니다.

1. `git status`로 충돌이 발생한 파일을 확인합니다.
2. 충돌 파일을 열어 `<<<<<<<`, `=======`, `>>>>>>>` 표시로 감싸진 부분을 찾습니다.
3. 둘 중 남길 코드를 직접 선택하거나 두 내용을 합쳐서 작성하고, 충돌 표시(`<<<<<<<` 등)를 모두 삭제합니다.
4. 프로그램을 실행해 정상 동작하는지 확인합니다.
5. `git add 파일명`으로 해결된 파일을 다시 스테이징합니다.
6. `git commit`으로 병합을 완료합니다.

- 추가한 프롬프트와 즐겨찾기 상태는 프로그램 실행 중에만 유지되며, 종료 시 초기화됩니다.
